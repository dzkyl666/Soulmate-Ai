1核心概念：会话记忆 ≠ 长期记忆

整个练习只有这一个东西需要真正想通，剩下都是体力活：

对比项会话记忆（项目本来就有）长期记忆（本次新增）
存哪data/sessions/<伴侣id>/<会话id>.jsondata/memory/<伴侣id>.json
归属某一个会话某一个伴侣
作用范围只在这个会话内跨会话、跨时间
内容每句话的原文模型抽取出的稳定事实
什么时候写每轮自动 append每轮对话后由模型判断该不该记
怎么读messages[-history_length:] 切片拼进 system prompt
换个会话❌ 归零（伴侣"失忆"）✅ 还在（伴侣"记得你"）
数据量会长到几百条应该只有几十条
一句话记住 会话记忆记的是「这次聊了什么」；长期记忆记的是「你是谁」。
为什么长期记忆不能直接把原文塞进去 会话原文又长又杂，全塞进 system prompt 会 ① 烧 token ② 淹没有效信息 ③ 每次都带一遍三年前那句"今天下雨了"。所以只留稳定的、关于人的事实。

llm.py 🆕 新增文件 模型调用层 · 145 行

为什么要单独抽一层

改之前，模型调用散在两个地方，各写一遍：

改之前的现状
companion_manager.py  →  build_client() + generate_ai_title() 里的 create()
main.py               →  聊天输入区里的 create() + 手写生成器

后果是「改一处忘一处」。而将来要加的东西全是横切关注点，会在两处同时发散：

  • Function Calling（要传 tools / tool_choice）
  • 超时与重试、生成参数（temperature / max_tokens）
  • 厂商差异（有的兼容端点不认某些参数）
  • 换 SDK / 换 LangChain

抽成一层之后，这些只改 llm.py 一处。

边界在哪（重要） llm.py 只认两样东西：① provider 配置字典（base_url / api_key / model / preset）；② 标准 messages 列表。 不认识"伴侣""会话""人设"这些业务概念。边界清楚才好替换。

对外 4 个函数

函数作用
resolve_api_key(provider)取 Key：界面填的优先，没填回退环境变量
build_client(provider, max_retries=None)建 OpenAI 客户端（必须显式传 base_url）
chat(provider, messages, system_prompt=None, ...)非流式，返回纯文本
stream_chat(provider, messages, system_prompt=None, ...)流式，逐字 yield

细节 ① system_prompt 单独抽成参数

而不是让调用方自己往 list 里塞 —— 这样"system 永远排最前面"这条格式规则只存在于一个地方。

llm.py · _build_payload()
def _build_payload(messages, system_prompt=None):
    payload = []
    if system_prompt:
        payload.append({"role": "system", "content": system_prompt})   # 永远排第一
    payload.extend(messages)
    return payload
这对应 LangChain 里的什么 ChatPromptTemplate.from_messages([("system", ...), MessagesPlaceholder("history"), ("human", ...)]) —— 那里也是把 system 和 history 分开声明的，同一个道理。

细节 ③ max_retries 是客户端级参数

llm.py · build_client()
def build_client(provider, max_retries=None):
    from openai import OpenAI
    kwargs = {"api_key": resolve_api_key(provider), "base_url": provider.get("base_url")}
    if max_retries is not None:
        kwargs["max_retries"] = max_retries      # 只能在客户端设，不能从 create() 传
    return OpenAI(**kwargs)
为什么留这个口子 SDK 默认失败重试 2 次。聊天时重试是好事（网络抖一下能自愈）， 但「记忆抽取」是顺手做的事，失败一次要白等 10 秒 —— 见 §5 的实测数据。

组件 A · EXTRACT_PROMPT（给模型看的抽取指令）

memory.py · 抽取提示词
EXTRACT_PROMPT = """你是记忆提取器。请从下面这段对话里，找出【值得长期记住的、关于用户的稳定事实】。

要记：名字与称呼、职业、所在地、家人与宠物、长期爱好、明确的喜好与禁忌、正在长期做的项目。
不要记：一次性的闲聊内容、助手自己说过的话、临时情绪、随时会变的小事。

只输出 JSON 数组，不要解释，不要 markdown 代码块。没有值得记的就输出 []。
示例：["用户叫李永康", "用户养了一只叫团子的猫", "用户不喝咖啡"]"""
三个设计要点（都踩过坑） ① 正反两面都举例 —— 只说"记什么"，模型会把闲聊也记进去。
② 强制 JSON 数组 + 明说不要代码块 —— 很多模型习惯性包一层 ```json，必须在提示词里先堵死。
③ 给它"什么都不记"的正当选项 [] —— 否则它会硬凑几条出来。

组件 B · parse_extraction() 兜住模型不听话

memory.py · 解析函数
def parse_extraction(raw: str) -> list:
    import json
    if not raw:
        return []
    text = raw.strip()

    # 1. 剥掉 markdown 代码块
    if text.startswith("```"):
        text = text.split("\n", 1)[-1]          # 去掉第一行的 ```json
        text = text.rsplit("```", 1)[0]         # 去掉结尾的 ```

    # 2. 只取第一个 [ ... ] 区间（防止模型前后加话）
    start, end = text.find("["), text.rfind("]")
    if start == -1 or end == -1 or end < start:
        return []
    text = text[start:end + 1]

    # 3. 解析
    try:
        data = json.loads(text)
    except Exception:
        return []
    if not isinstance(data, list):
        return []
    return [str(x).strip() for x in data if str(x).strip()]
核心原则 解析失败返回空列表，绝不抛异常。记忆是锦上添花，不该因为它把聊天带崩。

关键点 ②：add() 必须去重

为什么 每轮对话都抽一次，模型很容易反复抽出同一件事。不去重的话「用户叫李永康」会被记一百遍。

关键点 ③：to_prompt_block() 要限条数

memory.py · 注入文本
def to_prompt_block(self, limit: int = 30) -> str:
    facts = self.facts[-limit:]          # ← 只取最近 30 条
    if not facts:
        return ""
    lines = "\n".join(f"- {f.get('text', '')}" for f in facts)
    return (
        "\n\n【你记得关于 TA 的事】\n"
        f"{lines}\n"
        "像老朋友一样自然地把这些用上，但不要生硬地逐条复述。"
    )
为什么要 limit 记忆条数会随时间无限增长，全部塞进 system prompt 迟早烧光 token。 取最近 limit 条 —— 越近的记忆通常越相关。

⑤ 新增长期记忆业务方法（一整段，5 个方法）

📍 build_system_prompt() 之后、# 会话 sessions 之前
改后 · 新增段落
    # ══════════════════════════════════════════════════
    # 长期记忆（跨会话）
    # ══════════════════════════════════════════════════
    # 和「会话」的区别：
    #   会话记的是「这次聊了什么」—— 按 session_id 存，换个会话就没了；
    #   长期记忆记的是「你是谁」—— 按伴侣存，换会话、关程序、过一周都还在。
    def memory(self, companion_id=None):
        """拿到某个伴侣的记忆对象；没有伴侣时返回 None（界面层不用自己拼路径）"""
        cid = companion_id or self.current_companion_id
        return CompanionMemory(cid) if cid else None

    def memory_facts(self, companion_id=None):
        """读当前伴侣的全部长期记忆（侧边栏展示用）"""
        mem = self.memory(companion_id)
        return mem.facts if mem else []

    def forget_fact(self, fact_id, companion_id=None):
        """忘掉一条（侧边栏的 🗑️）"""
        mem = self.memory(companion_id)
        if mem:
            mem.remove(fact_id)

    def forget_all(self, companion_id=None):
        """全部忘掉"""
        mem = self.memory(companion_id)
        if mem:
            mem.clear()

    def remember_from_exchange(self, provider, companion, messages, keep_last=6):
        """从最近几轮对话里抽取「值得长期记住的事」写进长期记忆，返回新增条数。"""
        if not provider or not companion or not messages:
            return 0
        recent = messages[-keep_last:]
        convo = "\n".join(
            f"{'用户' if m.get('role') == 'user' else '伴侣'}：{m.get('content', '')}"
            for m in recent
        )
        try:
            raw = llm.chat(
                provider,
                [{"role": "user", "content": convo}],
                system_prompt=EXTRACT_PROMPT,
                temperature=0,        # 抽取要稳定、别发挥
                timeout=15,
                max_retries=0,
            )
        except Exception:
            return 0                  # 静默跳过

        mem = self.memory(companion.get("id"))
        if not mem:
            return 0
        return mem.add(parse_extraction(raw), session_id=self.current_session_id)

remember_from_exchange 的四个设计决定（面试能讲）：

#决定理由
①只喂最近 6 条，不是全部历史历史越长越烧 token；"该记住的事"通常就在刚才这几轮；更早的前几轮已经抽过
②失败一律静默（except 吞掉）记忆是锦上添花。网络一抖就失败，绝不能把「聊天」主流程带崩
③同步调用，不搞后台线程Streamlit 是"全量重跑"架构，没有常驻后台任务的位置。实测正常路径 0.7s，可接受
④timeout=15 + max_retries=0这条是实测加出来的 —— SDK 默认重试 2 次，抽取一旦失败要白等 10 秒

5踩坑速查

坑现象怎么解
模型不输出纯 JSON json.loads 抛异常，聊天崩 提示词里先堵死（"不要 markdown 代码块"）+ parse_extraction 三重兜底 + 失败返回 []
同一件事被记几十遍 记忆面板里刷屏 add() 里用 seen 集合去重
抽取失败卡 10 秒 回复完了界面还在转 max_retries=0（默认是 2）。注意它是客户端级参数，只能从 build_client 传
流式解析 IndexError 偶发 IndexError: list index out of range if not chunk.choices: continue
记忆改了下一轮不生效 要重启才能用上 不要缓存 facts，用 @property 每次现读盘；build_system_prompt 里现拼
换会话后伴侣失忆 长期记忆没起作用 检查 build_system_prompt 里那 6 行注入是否漏了；确认 data/memory/<伴侣id>.json 是按伴侣而不是按会话存
base_url 被环境变量劫持 请求发到别的地方 OpenAI SDK 会自己读 OPENAI_BASE_URL（你电脑上正好有这个变量）→ 必须显式传 base_url

6什么不该改（容易手痒的地方）

  • storage.py —— 它是通用文件读写（read_json / write_json / delete_file，还带原子写）。memory.py 复用它，一行都不用改。
  • llm.py —— 本次新增后，和记忆完全无关。它不管历史从哪来、存到哪去。将来加 Function Calling 才动它。
  • dialogs.py / theme.py —— 与本次无关。
  • 会话存储结构 —— data/sessions/<伴侣id>/<会话id>.json 保持原样，长期记忆是另起一套，不是改它。
  • 伴侣数据结构 —— 记忆不写进 companions.json。理由和昵称一样：记忆增长快、更新频繁，混进伴侣配置会让那个文件越来越大、还容易被误提交。
分层口诀（背下来就能应付面试） config 纯数据 → storage 纯读写 → memory / llm 两个能力层 → companion_manager 业务逻辑 → main / sidebar 界面。 界面层不 import memory，业务层不 import openai。
