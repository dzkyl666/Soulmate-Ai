# 安全说明

> 这份文档回答两件事：**这个应用防住了什么**、**部署时你必须做什么**。
> 最后附威胁模型与已知残余风险（不吹「绝对安全」）。

---

## 0. 一句话结论

v2 已具备部署到服务器的**基本安全基线**（认证、用户隔离、密钥加密、输入校验、限流、生产配置 fail-fast）。
但它是**自托管应用**：安全下限由你的部署方式决定 —— **必须放在 HTTPS 反代之后**，
且**必须设置强 `SOULMATE_APP_SECRET`**。

---

## 1. 已实现的防护

### 1.1 认证与授权

| 项 | 实现 |
|---|---|
| 口令存储 | bcrypt 哈希（自动加盐、慢哈希），**绝不存明文** |
| 口令强度 | 至少 8 位 + 大小写 + 数字（`core/security.password_strength`） |
| 登录态 | HMAC-SHA256 签名令牌，带过期时间；签名密钥由 `app_secret` 派生 |
| 防枚举 | 「用户不存在」与「密码错」返回**同一个** `InvalidCredentials` |
| 停用账号 | `UserRecord.disabled`，登录时拒绝 |
| 管理员 | `role` 字段；账号管理面板仅管理员可见 |
| 自助注册 | 可通过 `SOULMATE_ALLOW_SIGNUP=false` 关闭，改用 `soulmate create-user` |
| 登录限流 | `SOULMATE_RATE_LIMIT_LOGIN_PER_MINUTE`（默认 10 次/分） |

### 1.2 用户数据隔离

- 每个用户的数据在 `data/users/<用户名>/` 下，是**物理隔离**（不同路径）。
- 用户名经 `validate_username()` 校验（仅字母数字 `._-`），**不含路径分隔符**。
- 所有 ID（`companion_id` / `session_id`）经 `validate_id()` 校验并用于文件名拼接 ——
  这是**路径穿越**的防线：不允许 `../`。

### 1.3 密钥与敏感信息

| 项 | 做法 |
|---|---|
| API Key 落盘 | **Fernet 对称加密**（AES-128-CBC + HMAC），密文存 `api_key_enc` |
| 加密密钥来源 | 由 `SOULMATE_APP_SECRET` 经 PBKDF2-HMAC-SHA256（200k 次迭代、按用途分盐）派生 |
| 界面回显 | 只显示 `••••••1234`（`mask_secret`） |
| 日志脱敏 | 所有日志/异常文案先过 `redact()`：屏蔽 `sk-*`、Bearer、URL 内凭据、`api_key=` 形态 |
| 自动根密钥 | **仅非生产环境**自动生成到 `data/.app_secret`（权限 0600）；生产必须显式设置 |
| 密钥失效处理 | 解不开的 Key 置空并记警告，**不崩**（提示用户重填） |

> **为什么按用途分盐派生**：加密密钥与签名密钥共用一把是安全反模式，分开后一处泄露不直接波及其它用途。

### 1.4 输入校验与 SSRF 防护

- `base_url` 只允许 `http` / `https`，必须有主机名。
- **默认拒绝内网/回环/链路本地/保留地址** —— 防止「用户填一个 URL，服务器替他去请求内网」。
  确需接内网模型（Ollama、内网反代）时显式设 `SOULMATE_ALLOW_PRIVATE_BASE_URL=true`。
- 文本有长度上限（消息 8000 字、用途 200 字等），防 token 烧光与存储膨胀。
- 模型名拒绝换行/空字节。

#### 「内网地址」的判定口径（以及一个踩过的真坑）

判定**不直接使用 `ipaddress.is_private`**，而是显式列出真正的内网网段
（见 `core/validation.py` 的 `_INTERNAL_NETWORKS_V4 / _V6`）。

原因：`is_private` 的语义是 IANA 的「非全球可达」，比「内网」宽得多，
其中两段会造成**正常公网厂商被误拦**：

| 网段 | 为什么被 `is_private` 判为私有 | 实测后果 |
|---|---|---|
| `2001::/23` | 含 Teredo(`2001::/32`) 与基准测试段 | **`api.openai.com` 的 AAAA 记录是 `2001::c73b:9466`**，落在此段 → 「OpenAI 官方」预设会被本项目自己的 SSRF 检查拦掉 |
| `198.18.0.0/15` | 基准测试段 | 代理软件 **fake-IP 模式**常用它做域名映射 → 开 fake-IP 的用户所有厂商地址都被判成内网 |

这两段都不是「内网服务」：前者是历史过渡机制的地址，后者是**代理产物的映射**。
所以本项目把它们**排除**在「内网」之外，只保留真正的内网/本机/不可路由段：

- IPv4：`0.0.0.0/8`、`10/8`、`100.64/10`（CGNAT）、`127/8`、`169.254/16`、`172.16/12`、
  `192.0.0.0/24`、`192.168/16`、`224/4`（组播）、`240/4`（保留）
- IPv6：`::/128`、`::1/128`、`fc00::/7`（ULA）、`fe80::/10`、`ff00::/8`
- **IPv4 嵌进 IPv6 的四种写法都会先解出内嵌 IPv4，再递归判断** ——
  否则攻击者把内网地址「藏」进 IPv6 字面量就能绕过检查。覆盖情况：

  | 写法 | 例子 | 提取方式 |
  |---|---|---|
  | ① IPv4-mapped | `::ffff:127.0.0.1` | `IPv6Address.ipv4_mapped` |
  | ② IPv4-compatible（已废弃） | `::127.0.0.1` / `::7f00:1` | `::/96` 且非 `::`/`::1`，取低 32 位 |
  | ③ NAT64 well-known prefix | `64:ff9b::7f00:1` | `64:ff9b::/96`，取低 32 位 |
  | ④ 6to4 | `2002:7f00:1::` | `IPv6Address.sixtofour`（内嵌在第 2~3 组） |

  这四种**只判断内嵌的那 32 位是不是内网**，所以 `64:ff9b::808:808`（NAT64 指向 8.8.8.8）
  与 `2002:808:808::`（6to4 指向 8.8.8.8）仍然**放行** —— 不能一刀切把整个前缀算内网。

  **有意不处理 Teredo（`2001::/32`）**：它正是上面为了修 `api.openai.com` 误拦
  而从「内网」里排除的那一段（其 AAAA 记录落在 `2001::/23`）。Teredo 是过渡机制、
  目标是公网，不是内网服务；在这里解它的内嵌地址会把那个误拦重新引回来。

判定策略：域名解析出**多个地址时，只要其中存在内网地址就拒绝**（客户端可能挑中那一个）；
DNS 解析失败时 **fail-open 放行**（否则断网环境连本地模型都配不了）。
这层防护的定位是「挡住明显的 SSRF」，不是防火墙。

> 如果将来收紧这条口径（例如把 `198.18/15` 重新算作内网），
> 必须同步评估「fake-IP 用户会不会全被拦」。这个取舍是显式的，不是遗漏。
>
> 这四种嵌入写法与 Teredo 的取舍，在 `tests/test_core.py::TestIpv4EmbeddedInIpv6`
> 里有**双向**用例守着（该拦的 12 条 / 该放的 8 条）—— 只测单向会把误拦漏过去。

### 1.5 限流

进程内令牌桶，四档独立配额。**前三档按身份隔离**（key 带身份前缀，否则一人刷满会锁死所有人）：

| 入口 | 默认 | 接线点 | key 格式 |
|---|---|---|---|
| 聊天 | 30 次/分 | `LLMService.chat()` **和** `stream()` | `chat:{user_id}` |
| 记忆抽取 | 60 次/分 | `MemoryService.remember_from_exchange()` | `extract:{user_id}` |
| 登录 | 10 次/分 | `UserStore.authenticate()` | `login:{username}` |
| **开号** | 10 次/分 | `UserStore.bootstrap()` **和** `register()` | `register:global`（★ 全局桶） |

「接线点」列出来是有原因的：本项目的限流曾经**模块、配置、测试、文档四件套齐全，
但生产代码零调用**（空转），而当时的验收脚本因为只做「文件/字符串存在性」检查而没抓到。
现在有 25 条**调用链**测试专门证明它真的挂在业务链上（`tests/test_ratelimit_wiring.py`），
`scripts/verify.py` 也会用 AST 断言这些文件里真的出现了 `get_limiter()` 调用。

**开号那档为什么是全局桶**：注册时攻击者会**不断换用户名**，按 username 记账
等于每条都从空桶开始 —— 记了等于没记。全局桶限制的是「整个进程每分钟最多开多少个号」，
这才是真实风险面。代价是理论上可被用来阻塞他人注册；对个人 / 小团队应用可接受，
且生产环境的首要控制是 `SOULMATE_ALLOW_SIGNUP=false`（`SOULMATE_ENV=production` 时强制校验）。
首启（`bootstrap()`）也走这一档 —— 「谁先到谁当管理员」的窗口不该完全不设速率。

#### 三个如实记录的取舍（别假装不存在）

**① 登录限流用 `login:{username}`，可被用来「定向锁死某个账号」**

认证发生时用户**尚未登录**，拿不到 `user_id`，只能用「他声称是谁」。
代价：攻击者只要针对 `admin` 刷满配额，真正的管理员在窗口内（1 分钟）也登不进来 ——
一种拒绝服务型的副作用。

这是标准取舍。备选方案是叠加客户端 IP，但 Streamlit 侧拿真实 IP 不可靠
（反代下会拿到代理 IP，还需信任 `X-Forwarded-For`）。
缓解手段：在反向代理层对 `/` 做 IP 级限流或接入 WAF（见第 2 节部署清单）。

**② 一次记忆抽取会消耗**两档**配额**

抽取内部调用的是 `llm.chat()`，所以它同时记 `extract:` 和 `chat:` 两笔账。
后果：默认值下（chat=30、extract=60），**每发一条消息会消耗 3 次配额**
（1 次 stream + 1 次 extract + 1 次抽取内部的 chat），
也就是「聊天 30 次/分」实际约等于**每分钟 15 条消息**。

这不是 bug，是有意的（抽取=额外一次模型调用，确实该计入调用预算），
但默认值 `extract(60) > chat(30)` 意味着 `extract` 档**永远不会先触发**，
它实际是个冗余的第二道闸。若你希望两档各自独立生效，可把
`SOULMATE_RATE_LIMIT_EXTRACT_PER_MINUTE` 调到低于 `chat` 档。

> 想彻底解耦，需要给抽取走一条「不计 chat 档」的内部通道 ——
> 那会引入一个"内部调用"语义，当前规模不值得。

**③ 开号限流是全局桶，可被用来「阻塞他人注册」**

开号档用 `register:global` 而不是按用户名（理由见上：换用户名就能绕过）。
代价：把全局配额刷满，真用户这一分钟内也注册不了。

之所以接受：真有人刷号时，本来就该先停下来；而且生产环境的首要控制不是限流，
而是 `SOULMATE_ALLOW_SIGNUP=false` 这个开关（生产强制校验）。
另外**首启抢管理员**（谁先到谁是 admin）这个固有窗口，限流只能降低速率、
不能消除 —— 它靠的是部署时尽快完成初始化，不是靠限流。

> 刻意**没有**把注册档按 IP 限流：Streamlit 侧拿真实客户端 IP 不可靠
> （反代下是代理 IP，还要信任 `X-Forwarded-For`），做成不可靠的防护
> 比明确不做更危险 —— 会让人误以为有了 IP 维度的保护。

### 1.6 生产配置 fail-fast

`SOULMATE_ENV=production` 时，以下任一情况会**拒绝启动**（而不是带病运行）：

- `SOULMATE_APP_SECRET` 未设置 / 短于 32 字符 / 是常见弱值
- `SOULMATE_DEBUG=true`
- 使用本机账号且 `SOULMATE_ALLOW_SIGNUP=true`（任何人可开号）

### 1.7 容器与依赖

- 镜像**非 root 运行**（uid 10001）、`no-new-privileges`、`cap_drop: ALL`
- compose 默认只监听 `127.0.0.1:8501`（不直接暴露公网）
- CI 里跑 ruff 的 **bandit 规则集**（`S` 前缀）扫常见安全问题

## 2. ★ 部署安全清单（照着做）

### 必做

- [ ] **设置强 `SOULMATE_APP_SECRET`**：`python -c "import secrets; print(secrets.token_urlsafe(48))"`
- [ ] **放在 HTTPS 反向代理之后**（Nginx/Caddy）。裸 HTTP 会让登录口令与令牌明文过网
- [ ] `SOULMATE_ENV=production`
- [ ] `SOULMATE_ALLOW_SIGNUP=false`，用 `soulmate create-user` 开号
- [ ] `SOULMATE_DEBUG=false`
- [ ] 数据目录**只给服务账号读写**；定期备份（见 DEPLOYMENT.md）
- [ ] 不把 `data/`、`.env`、`.streamlit/secrets.toml` 提交到任何仓库
      （`.gitignore` 与 pre-commit 已挡，但别绕过）

### 强烈建议

- [ ] 反向代理层再加一层访问控制（IP 白名单 / Basic Auth / SSO），做纵深防御
- [ ] 开启 fail2ban 或云厂商 WAF，挡住登录爆破
- [ ] 定期 `docker compose pull && up -d --build` 更新依赖（`pip-audit` 可扫已知漏洞）
- [ ] 用 `soulmate doctor` 在启动流程里做自检
- [ ] 数据目录加密（如 LUKS / BitLocker），防磁盘被物理拿走

### 别做

- [ ] ❌ 不要把 `data/` 直接挂到公网可访问的静态目录
- [ ] ❌ 不要多个副本共用同一个 `data/`（JSON 文件非并发安全）
- [ ] ❌ 不要在未设 `APP_SECRET` 的情况下跑生产 —— 一重启密钥就变，已存 Key 全部解不开

## 3. 威胁模型

### 防住的

| 威胁 | 缓解 |
|---|---|
| 数据库/文件泄露导致 API Key 泄露 | Key 加密落盘；密钥与数据分离（`APP_SECRET` 在环境变量/密钥管理里） |
| 撞库 / 口令爆破 | bcrypt 慢哈希 + 登录限流 + 统一错误文案 |
| 用户名枚举 | 统一错误文案 |
| 越权访问他人数据 | 物理目录隔离 + ID 校验（无路径穿越） |
| 服务端被当作 SSRF 跳板 | 默认拒绝内网地址 |
| 日志泄露密钥 | 全出口 `redact()` |
| 刷接口烧钱 | 三档限流 + 单条消息长度上限 |
| 误把密钥提交到仓库 | `.gitignore` + pre-commit 钩子 + `.dockerignore` |
| 配置疏漏上生产 | `validate_for_startup()` fail-fast |

### 不在防护范围内（诚实说明）

| 情况 | 说明 |
|---|---|
| **提示注入（Prompt Injection）** | 聊天内容与长期记忆会进 system prompt。恶意用户可尝试让模型「忘记人设」或越权输出。**缓解**：所有输出只回到该用户自己的会话，不会跨用户；不接工具调用，所以无法通过注入触发服务端动作。**这是 LLM 应用的共性残余风险。** |
| **拿到宿主机 root 的攻击者** | 能读 `APP_SECRET` 就能解密 Key。这类攻击者已越过应用边界，需靠主机安全解决 |
| **恶意模型供应商** | 你填的 Base URL 是该供应商的服务器，它会看到你发过去的对话内容。**只填你信任的服务商。** |
| **DDoS / 大流量** | 应用内限流挡不住 L4/L7 洪水，需在反代或云厂商层解决 |
| **多副本下的限流** | 进程内令牌桶各算各的。多副本部署需换 Redis 共享存储 |
| **传输中加密** | 应用自身不做 TLS，**必须**由反代终结 HTTPS |

## 4. 密钥管理

### 生成

```bash
python -c "import secrets; print(secrets.token_urlsafe(48))"
```

### 存放

| 环境 | 建议 |
|---|---|
| 本地开发 | 不设，自动生成到 `data/.app_secret` |
| Docker | `.env` 文件（已在 `.gitignore`），或 `docker secret` / 云厂商 Secret Manager |
| K8s | `Secret` 挂成环境变量，不要写进镜像 |

### 轮换的代价（重要）

`APP_SECRET` 一旦更换：

- **已加密的 API Key 全部解不开**（会置空并提示重填，不会崩）
- **所有人登录态失效**（需要重新登录）

所以：把它当长期密钥管理，别随手改。真要轮换，流程是
「备份 `data/` → 换密钥 → 逐个重填 API Key → 通知用户重新登录」。

---

## 5. 事件响应

怀疑密钥泄露时：

1. **立即轮换 `APP_SECRET`**（并接受上面说的代价）
2. **去各模型供应商后台吊销旧 API Key**（这一步比换 APP_SECRET 更紧急 ——
   泄露的若是明文 Key，加密与否已无意义）
3. 检查 `data/logs/soulmate.log` 是否有异常登录/调用
4. 审查 `data/users.json` 是否有多出来的账号
5. 若数据目录被篡改，从 `backups/` 恢复
